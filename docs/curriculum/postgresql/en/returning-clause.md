Applications often need values produced by a write—generated ids, defaults, trigger-adjusted values, or the rows that were changed. PostgreSQL can return them from the mutation itself.

## Mental model

Without `RETURNING`:

```text
INSERT -> success -> run another SELECT to discover generated values
```

With `RETURNING`:

```text
INSERT -> PostgreSQL writes row -> same statement returns requested columns
```

The RETURNING list behaves like a SELECT output list over the rows affected by the mutation.

## Predict before you run

Ids 1 and 2 already exist. The identity column generates 3 for Dune, so predict one returned row: `(3, 'Dune')`.

## Worked example

```sql
INSERT INTO movies (title)
VALUES ('Dune')
RETURNING id, title;
```

| id | title |
| ---: | --- |
| 3 | Dune |

This avoids a separate read just to discover the generated id. `RETURNING` is also available on UPDATE and DELETE, and modern PostgreSQL supports it with MERGE as well.

## Debug this

```sql
INSERT INTO movies (title) VALUES ('Dune');
SELECT id, title FROM movies WHERE title = 'Dune';
```

This can work, but the second statement is an extra round trip and may require a reliable way to identify exactly the row just written. When the changed row itself is what you need, RETURNING expresses that intent directly.

## Common mistakes

- Thinking RETURNING runs before the mutation; it reports rows actually affected by it.
- Fetching generated values with an avoidable second query.
- Returning every column by habit when the application only needs a small subset.

## Your turn

Insert Dune and return its generated `id` plus `title` from the same statement.

## Quick check

What practical problem does `RETURNING id` solve after an INSERT with a generated identity?

**Answer:** it gives the generated id directly from the write, avoiding a separate lookup query.
