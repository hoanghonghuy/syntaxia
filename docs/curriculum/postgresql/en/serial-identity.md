PostgreSQL can generate key values automatically. In modern schemas, `GENERATED ... AS IDENTITY` expresses that intent directly and owns an implicit sequence behind the column.

## Mental model

```sql
CREATE TABLE movies (
  id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title TEXT
);
```

Write flow:

```text
INSERT title only -> identity sequence supplies next id -> row stored
```

After ids 1 and 2 exist, omitting `id` on the next insert produces id 3.

`SERIAL` is older PostgreSQL shorthand that also creates sequence-backed auto-number behavior. You should recognize it in existing databases, but use identity columns when designing modern schemas unless project constraints require otherwise.

## Predict before you run

The next generated id is 3. Predict the complete table after inserting only the title `Dune`.

## Worked example

```sql
INSERT INTO movies (title)
VALUES ('Dune');
```

| id | title |
| ---: | --- |
| 1 | Inception |
| 2 | The Matrix |
| 3 | Dune |

## Debug this

```sql
INSERT INTO movies (id, title)
VALUES (3, 'Dune');
```

With `BY DEFAULT` this can be allowed, but it defeats the purpose of this exercise and can create sequence/key-management surprises if explicit ids are used carelessly. Let the identity mechanism own normal id allocation.

## Common mistakes

- Treating generated ids as values application code must always calculate itself.
- Learning only `SERIAL` and missing the explicit identity syntax in modern PostgreSQL schemas.
- Assuming generated values alone guarantee all business uniqueness; the key/constraints still define integrity.

## Quick check

Which schema feature is the clearer modern declaration for generated key values: `IDENTITY` or `SERIAL`?

**Answer:** `GENERATED ... AS IDENTITY`; `SERIAL` remains common legacy shorthand you should still recognize.
